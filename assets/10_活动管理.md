## 一、模块定位

### 1.1 模块概述

活动管理是连心现有核心模块，覆盖活动创建→发布→报名→签到→回顾全生命周期。是客户使用频次最高的模块之一，与会员管理并列为两大核心业务场景。

**重构核心问题：**

1. **配置体验差**：7步线性向导，必须按顺序走完，不可跳转不可回退；表单样式固定无法品牌化；每次从零创建无法复用
2. **高并发不稳定**：大型活动（维园家乡市集、关爱队地区活动）开抢瞬间崩溃率\~15%
3. **运营能力缺失**：无渠道归因、签到低效、审批逐条操作

### 1.2 在闭环中的角色

```
数据采集 ──► 活动报名/签到数据回写会员画像 ★
                    │
画像 ──► RFM分层 ──► 圈选 ──► 规则引擎
                                      │
                          触达动作：活动推荐（指向本模块）
                                      │
                          效果归因 ← 活动渠道UTM追踪 ★
```

活动管理在闭环中的双重角色：

- **数据源**：活动报名/签到/参与数据是RFM分层R和F维度的核心输入
- **触达终点**：规则引擎的"活动推荐"动作指向活动，渠道归因（UTM）追踪触达→报名转化

### 1.3 增强目标

| 目标 | 指标 | 现状 | 目标值 |
|-|-|-|-|
| 创建效率 | 活动创建时间 | \~30分钟 | \~5分钟（6x提升） |
| 配置体验 | 创建流程模式 | 7步线性向导（不可跳转不可回退） | 3区并行配置（自由切换+实时预览） |
| 品牌自主性 | 表单样式自定义 | 固定UI，无法品牌化 | 完全自定义（品牌色/背景图/字体） |
| 复用效率 | 模板创建占比 | 0%（每次从零） | ≥60%活动从模板创建 |
| 系统稳定性 | 峰值崩溃率 | \~15% | <0.1%（可用性99.9%+） |
| 归因能力 | 渠道归因 | 无 | 全渠道UTM追踪 |
| 签到效率 | 签到速度 | 5秒/人（人工核对） | 1秒/人（扫码签到） |
| 审批效率 | 批量审批 | 逐条审批 | 批量审批+信息修改 |
| 商业化 | 模板库分层 | 无 | 按付费等级开放模板范围 |

#### 3.1.2 增强需求

**A. 3区并行配置模式（核心重构）**

旧版7步线性向导→新版3区并行配置：

| 区域 | 包含内容 | 交互方式 |
|-|-|-|
| **基础信息区** | 活动名称/类型/时间/地点/开放度/报名规则/活动详情头图/费用/名额 | 表单填写，可随时切换至其他区 |
| **表单&样式区** | 左侧：表单画布（拖拽排版）+ 样式设置（品牌色/背景图/字体）；右侧：常用字段库+高级字段 | 拖拽式，所见即所得 |
| **预览&发布区** | 实时预览用户端效果（桌面+移动）+ 一键发布 + 草稿保存 | 预览+操作 |

**关键设计原则：**

- 管理员可自由在3个区域间切换，任何修改实时同步到预览
- 不强制按顺序完成——可直接跳到样式区调品牌色，再回基础信息区填内容
- 预览区始终可见最小化缩略图，点击展开完整预览

| 报名模式 | 说明 | 场景 |
|-|-|-|
| **为自己报名** | 会员报名自己参加 | 默认模式 |
| **为他人报名** | 会员代替非会员报名（填写他人信息） | 为家人/朋友报名 |
| **为同行人报名** | 一次操作为自己+N位同行人报名 | 家庭活动/团体参与 |

**为他人报名约束：**

- 需填写被报名人信息（姓名+手机号+自定义字段）
- 被报名人如果是会员，自动关联会员档案
- 被报名人如果不是会员，创建临时档案（不自动入会）

**为同行人报名约束：**

- 同行人数量可配置上限（默认10人）
- 每位同行人需填写必填字段
- 一次性支付总费用
- 签到时每人独立签到

### 3.4 高并发优化（新增）

#### 3.4.1 优化方案

| 层级 | 方案 | 说明 |
|-|-|-|
| **前端** | CDN缓存 | 活动详情页静态资源CDN分发，减少源站压力 |
| **接入层** | 排队机制 | 报名开放瞬间先入队列再逐步放行，避免瞬间压垮后端 |
| **缓存层** | Redis缓存 | 热门活动数据（名称/名额/报名人数）缓存到Redis，读请求不穿透到DB |
| **数据库** | 读写分离 | 活动详情读请求走从库，报名写请求走主库 |
| **弹性** | 自动扩容 | 峰值期自动增加应用实例，流量回落后缩容 |

**排队机制流程：**

```
用户点击报名
→ 前端请求进入排队网关
→ 返回排队位置（"您排在第23位，预计等待5秒"）
→ 后端按队列顺序逐步处理报名请求
→ 报名成功→跳转支付 / 名额已满→提示"名额已满"
```

**性能目标：**

| 指标 | 目标值 |
|-|-|
| 10万级并发报名 | 可用性99.9%+，零崩溃 |
| 单个报名请求响应 | ≤3秒 |
| 排队等待时间 | ≤30秒 |

### 3.11 报名条件引擎（新增，替代3.2固定开放度）

#### 3.11.1 设计思路

当前3.2节的活动开放度是4级固定档位（公开/注册/会员/等级），无法满足灵活组合的准入需求。新增**可组合的报名条件引擎**，管理员可自由配置5大类条件，支持AND/OR逻辑组合。

> 3.2节的4级开放度作为**快速预设**保留（一键选择常见组合），条件引擎作为**高级模式**提供精细控制。

#### 3.11.2 条件类别

| 条件类别 | 具体条件 | 说明 |
|-|-|-|
| **身份门槛** | 无需登录(游客可报) | 不要求登录即可报名 |
| | 需登录 | 登录用户才可报名 |
| | 需本机构会员 | 仅本机构会员可报名 |
| | 需上级机构会员(集团会员) | 上级机构（总会/联会）会员可报名 |
| **会员属性** | 指定会员类型 | 如仅"普通会员"或"理事会员"可报名 |
| | 指定会员等级 | 如仅"金卡会员"及以上可报名 |
| | 指定标签 | 如带"活跃志愿者"标签的会员可报名 |
| **人口属性** | 年龄范围 | 如18-65岁 |
| | 性别 | 如仅限女性 |
| | 地址/地区 | 如仅限某区居民 |
| **行为门槛** | 已消费金额≥X | 历史消费总额达到门槛 |
| | 已参与活动数≥X | 历史活动参与次数达标 |
| | 签到率≥X% | 历史活动签到率达标 |
| | 签到次数≥X | 历史签到总次数达标 |
| | 积分≥X | 当前积分余额达标 |
| **报名控制** | 每人限报次数 | 如每人限报1次该活动 |
| | 重复报名限制 | 同一活动不可重复报名 |
| | 报名冷却期 | 上次取消报名后N天内不可再次报名 |

#### 3.11.3 逻辑组合

- 多个条件之间支持 **AND（全部满足）** 和 **OR（任一满足）** 逻辑
- 支持分组嵌套：如 (身份=会员 AND 等级≥金卡) OR (身份=集团会员 AND 标签含"特邀")
- 条件引擎提供可视化条件构建器，类似规则引擎的Trigger配置界面

#### 3.11.4 不满足条件时的引导动作

| 不满足条件 | 引导动作 |
|-|-|
| 需登录 | 弹出登录引导 |
| 需本机构会员 | 弹出入会引导，展示会员权益 |
| 需上级机构会员 | 提示"请联系所属机构确认会员资格" |
| 会员等级不足 | 弹出升级引导，展示等级权益对比 |
| 年龄/性别不符 | 提示"本活动报名条件：XX" |
| 行为门槛不足 | 提示"还需参与N次活动/签到N次即可报名" |
